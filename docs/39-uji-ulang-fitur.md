# Uji Ulang Fitur Setelah Deploy

Gunakan akun dan data uji milik sendiri untuk lima role: `super_admin`, `admin` pembimbing, `school`, `intern` aktif, dan `applicant`. Siapkan dua sekolah dengan siswa berbeda, dua pemilik lampiran privat, serta akun belum aktif. Jalankan di host yang baru dideploy melalui backend mandiri; uji otomatis lokal tidak menggantikan uji pada host production. Catat waktu WIB, role/akun, kasus, status HTTP, hasil aktual, dan PASS/FAIL tiap kasus. Jangan unggah data pribadi atau surat dokter asli.

| Kasus | Langkah | Hasil yang diharapkan |
| --- | --- | --- |
| Login lima role | Login bergantian sebagai `super_admin`, `admin`, `school`, `intern`, dan `applicant`; buka dashboard dan fitur sesuai role, lalu logout. | Setiap role mendapat akses sesuai permission; cookie sesi HTTPS memakai `Secure`; sesi yang sudah logout tidak dapat dipakai ulang. |
| Akses negatif role | Tanpa login, panggil API terlindungi. Dengan akun `admin`, `school`, `intern`, dan `applicant`, panggil langsung API khusus super-admin, termasuk operasi tulis. | Anonim mendapat 401; setiap role tanpa permission mendapat 403; tidak ada data atau perubahan yang lolos melalui URL/API langsung. |
| Aktivasi akun | Dengan akun belum aktif, jalankan undangan/aktivasi melalui email uji dan tetapkan password valid; coba token salah, kedaluwarsa, dan pemakaian ulang token. | Aktivasi valid memungkinkan login sesuai role yang diberikan; token tidak valid ditolak tanpa mengaktifkan akun atau membuat sesi; tidak ada peningkatan role. |
| Portal sekolah dan isolasi | Sebagai `school` A, lihat siswa sekolah A. Ubah ID/filter pada URL/API untuk membaca siswa, absensi, laporan, atau lampiran sekolah B; coba operasi tulis tanpa permission. | Hanya data dalam lingkup sekolah A terlihat; akses lintas sekolah dan tulis terlarang ditolak tanpa membocorkan data atau mengubahnya. |
| Applicant | Sebagai `applicant`, buka dan perbarui pendaftaran sendiri; coba baca/ubah pendaftaran applicant lain dan panggil API intern sebelum mendapat hak akses. | Pendaftaran sendiri tersimpan sesuai tahap; akses lintas pemilik dan fitur tanpa permission ditolak; role tidak berubah lewat input pengguna. |
| Buat user | Sebagai `super_admin`, buka `/dashboard/super-admin/users`. Coba password <12 karakter dan role kosong, lalu buat intern dengan email unik, password 12–128 karakter, dan role Intern. | Input buruk ditolak dengan pesan jelas; akun valid muncul di daftar, bisa login dan membuka dashboard intern. Tidak ada POST 500. |
| Duplikat email | Ulangi pembuatan memakai email uji yang sama. | Pesan “Email sudah digunakan”; tidak muncul akun/profil ganda. |
| Upload laporan | Sebagai intern, buka `/dashboard/intern/daily-reports`. Buat laporan hari ini (pekerjaan ≥10 karakter), lampirkan PDF/gambar atau DOCX kecil; buka ulang dan revisi. Coba file > batas UI (gambar 5 MB; dokumen 10 MB). | Laporan dan lampiran tersimpan, bisa dibaca sesuai hak akses; revisi tersimpan; file terlalu besar ditolak. |
| Absensi dan GPS | Aktifkan izin lokasi dan kamera, buka `/dashboard/intern/attendance`. Check-in dengan selfie, periksa koordinat/jam/tanggal WIB; check-out dengan selfie. Ulangi saat izin lokasi dimatikan. | Check-in/out tercatat satu kali pada tanggal WIB yang tepat; tanpa GPS tombol tidak bisa dipakai; lokasi di luar geofence meminta alasan dan bukti saat check-in atau menolak check-out. |
| Izin/sakit | Ajukan izin dua hari tanpa lampiran; ajukan sakit dengan surat uji; admin menyetujui/menolak dari `/dashboard/admin/attendance`. Coba setujui izin pada tanggal intern sudah check-in. | Persetujuan membuat entri izin per hari; sakit perlu lampiran; penolakan tidak membuat entri; bentrok kehadiran ditolak (HTTP 409), data hadir tidak tertimpa. |
| Review laporan | Sebagai `admin` pembimbing, buka laporan siswa yang menjadi tanggung jawabnya, beri review/revisi, lalu cetak. Sebagai intern lain, coba baca/ubah laporan tersebut lewat ID langsung. | Review dan hasil cetak sesuai data serta lingkup pembimbing; intern lain tidak dapat membaca atau mengubah laporan. |
| Lampiran dan signed URL privat | Sebagai pemilik/role berwenang, minta signed URL dan buka lampiran privat. Sebagai pemilik lain, coba minta signed URL, baca path mentah tanpa token, serta ubah/hapus objek; coba signed URL dengan token diubah atau kedaluwarsa. | URL valid dapat dibaca selama masa berlaku; penerbitan URL dan mutasi lintas pemilik ditolak; path tanpa token serta token rusak/kedaluwarsa tidak membuka file. Signed URL diperlakukan sebagai secret dan tidak dicatat di tiket. |
| LMS pembimbing dan intern | Sebagai `admin` berwenang, kelola course, materi/lampiran, enrollment, kuis, dan assignment. Sebagai intern terdaftar, buka materi, kerjakan kuis, kirim assignment, lalu periksa progres dan sertifikat setelah syarat terpenuhi. Coba course tanpa enrollment serta jawaban/submission intern lain lewat ID langsung. | Alur belajar, penilaian, progres, dan sertifikat konsisten; lampiran sesuai hak akses; course/submission tanpa izin ditolak; sertifikat tidak terbit sebelum syarat terpenuhi. |
| Audit log | Sebagai `super_admin`, cocokkan perubahan user/role dan tindakan admin yang diaudit dengan log. Sebagai `school`, `intern`, dan `applicant`, coba baca API audit langsung serta ubah/hapus log. | Log memuat aktor, aksi, target, dan waktu yang sesuai tanpa password/token; akses tanpa permission serta perubahan/penghapusan tanpa izin ditolak. |

Semua kasus wajib memiliki hasil tercatat untuk role terkait. Tandai kasus yang terblokir sebagai belum lulus beserta penyebabnya. Checklist ini melengkapi `roleSmoke`; probe endpoint saja belum membuktikan perjalanan pengguna. Gunakan hasil UAT bersama paket tepat 11 evidence pada `docs/33-selfhosted-uat-performance-gate.md` untuk penilaian readiness.

Jika gagal: ambil waktu WIB, akun uji, URL request, status HTTP, dan log container `api` serta `web` pada waktu yang sama. Jangan salin password, cookie, token, selfie, atau isi lampiran ke tiket.
