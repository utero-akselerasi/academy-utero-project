# Runbook pemisahan kredensial Supabase Phase 13

**Status: NO-GO; rencana saja.** Dokumen ini tidak memberi izin mengubah host, menerbitkan kunci, menghentikan writer, atau memulai maintenance. Pemilik kedua instance dan semua workload bersama harus menyetujui rencana, jadwal, masa tenggang sesi, serta pemulihan sebelum operator melakukan tindakan live. Jangan menaruh nilai rahasia, JWT, hash rahasia, keluaran `docker compose config`, atau file env privat dalam tiket/repo/log.

## Ruang lingkup dan risiko

| Lingkungan | Supabase self-hosted | Aplikasi Academy | Endpoint |
| --- | --- | --- | --- |
| Develop | `20.20.20.173`, dipakai aplikasi lain | `docker-compose.develop.yml`, project `website-academy-utero-develop`, web `utero_academy_develop_web`, nginx `utero_academy_develop_nginx` | `https://supabase.carubra.com` (container memetakan hostname ke IP develop); nginx `127.0.0.1:9983` |
| Production | `20.20.20.3`, dipakai aplikasi lain | `docker-compose.yml`, project `website-academy-utero`, web `utero_academy_web`, nginx `utero_academy_nginx` | `https://supabase.carubra.space`; nginx port host `9982` |

Audit 14 Oktober 2026 (`docs/29-production-readiness-2026-10-14.md`) menemukan material `JWT_SECRET`, `ANON_KEY`, dan `SERVICE_ROLE_KEY` **identik** pada kedua host. JWT bertanda tangan dari satu lingkungan dapat diterima lingkungan lain jika verifier memakai secret sama; service-role melewati RLS. Perbedaan hostname, DB, atau Docker network bukan batas kriptografis. Semua aplikasi, pekerja terjadwal, webhook, integrasi, dan operator yang memakai anon/service-role atau bearer JWT pada **masing-masing** host harus diinventarisasi oleh pemilik platform; daftar Academy di atas bukan inventaris lengkap workload bersama. Catat pemilik, lokasi konfigurasi, jenis credential, masa berlaku token, mekanisme refresh, waktu deploy dan jalur rollback tanpa mencatat nilainya. Konfirmasi juga direct DB clients, Edge Functions, Realtime, dashboard/admin tooling, dan pipeline CI bila digunakan.
Audit Docker read-only saat ini mengidentifikasi sembilan komponen aktif pada masing-masing host: `supabase-db`, `supabase-auth`, `supabase-rest`, `supabase-edge-functions`, `supabase-storage`, `supabase-studio`, `realtime-dev.supabase-realtime`, `supabase-pooler`, serta gateway `supabase-kong` (develop) atau `supabase-envoy` (production). Jalankan `npm run audit:phase13-runtime-credentials` dari workstation operator untuk membandingkan credential JWT/anon/service-role/metrics serta key publishable/secret/asymmetric modern di runtime semua komponen tersebut dan antar-host. Gate juga memastikan JWKS PostgREST memuat key HS256 yang ekuivalen dengan secret host dan menolak EC public key yang tetap identik lintas host; key ES256 tambahan bukan mismatch bila berbeda. Perintah hanya mengeluarkan `GO`/`NO-GO`, tetapi memproses env container yang sensitif di memori lokal melalui SSH; jangan capture stdout mentah `docker inspect` atau jalankan melalui logger yang merekam data subprocess. Lulus audit ini belum membuktikan seluruh consumer eksternal telah beralih atau JWT lama telah dicabut.

## Persetujuan dan gerbang sebelum eksekusi

1. Pemilik Supabase develop dan production, pemilik seluruh writer bersama, keamanan, serta pemilik aplikasi menyetujui secara tertulis urutan host, outage/session policy, jendela maintenance, penanggung jawab tiap komponen, dan kriteria GO/NO-GO. Operator dan reviewer berbeda; tidak ada rotasi sepihak. Tandai production tetap NO-GO sampai develop stabil dan gate Phase 13 lain terpenuhi.
2. Inventarisasi konfigurasi pada **kedua** host: sumber `JWT_SECRET`, pasangan anon/service-role yang ditandatangani, gateway Kong (consumer/credential dan route), Auth/GoTrue (termasuk token refresh dan OAuth), PostgREST, Storage (termasuk signed URL), Realtime, Functions, serta layanan lain yang menandatangani atau memverifikasi JWT. Pastikan proses, secret store, klien dan proxy mana yang perlu restart/redeploy. Jangan menganggap perubahan satu file env otomatis menyinkronkan semuanya.
3. Uji rehearsal pada clone terisolasi dengan data terlindungi: kunci berbeda per host, kecocokan key dengan secret masing-masing, RLS allow/deny, service-role, login/refresh/logout, upload/download/signed URL, Realtime/Functions bila dipakai, dan workload non-Academy. Uji restore **DB/Auth/roles/ACL/config dan byte Storage** beserta aplikasi dan secret store, bukan hanya dump SQL. Simpan bukti verifikasi dan pemetaan artifact privat yang dapat dipakai untuk rollback.
4. Jadwalkan freeze seluruh writer ke host target (DB write, Auth signup/refresh bila perlu, Storage upload, job, webhook dan antrean). Verifikasi semua sumber tulis berhenti; nol transaksi sesaat bukan bukti freeze. Di jendela sama ambil backup final konsisten DB/Auth/roles/config dan seluruh byte Storage, hash dan uji restore replacement. Snapshot read-only sebelumnya bukan backup cutover. Jika freeze/backup/restore atau persetujuan gagal, **STOP** sebelum mengubah kunci.

## Urutan rotasi terkoordinasi (hanya setelah GO tertulis)

1. Tetapkan pasangan **baru dan berbeda** untuk tiap lingkungan: `JWT_SECRET` develop ≠ production; turunkan/terbitkan `ANON_KEY` dan `SERVICE_ROLE_KEY` untuk secret host masing-masing, dengan role JWT yang benar (`anon`, `service_role`). Simpan lewat secret store privat berakses terbatas; jangan memakai ulang pasangan dari host lain. Kunci anon/service-role lama yang identik tidak boleh tetap valid pada salah satu host setelah isolasi selesai. Rotasi ini tidak memisahkan data atau hak akses DB dengan sendirinya.
2. Pada jendela develop yang disetujui, freeze dan backup sesuai gerbang; siapkan atomik konfigurasi baru untuk Kong, Auth, PostgREST, Storage, Realtime, Functions dan konsumen lain pada `20.20.20.173`. Sinkronkan signer/verifier dengan gateway dan semua pemakai key; restart/redeploy sesuai dependency, cek health sebelum melepas freeze. Jangan pernah memasang key baru pada gateway sambil membiarkan verifier lama, atau sebaliknya. Production masih memakai konfigurasi lama selama tahap develop: **selama itu isolasi dua arah belum tercapai**, batasi akses lintas lingkungan dan jangan menyatakan GO keamanan.
3. Rebuild dan redeploy **kedua** aplikasi Academy untuk host masing-masing dalam jendela terkait. Pada develop cocokkan `.env.develop.build` (nilai publik yang dibake saat build) dengan `.env.develop` runtime termasuk URL/anon; pada production cocokkan `.env.production.build` dengan `.env.production` runtime. `NEXT_PUBLIC_*`/anon dan URL yang dibake tidak berubah hanya dengan restart; service-role hanya di runtime server, tidak di bundle publik. Periksa marker target build, binding URL/TLS/IP, dan startup check; image production lama diketahui mengarah ke develop. Jangan gabungkan Compose develop dan production atau menjalankan `docker compose down` tanpa file target eksplisit.
4. Uji develop dengan token nyata baru: anon, service-role hanya server-side, Auth login/refresh, JWT/RLS allow/deny, Storage byte/API/signed URL, dan workload bersama; catat kegagalan, lama propagasi, dan owner sign-off. Setelah develop stabil serta gate Phase 13 terpenuhi, ulangi freeze, backup final, restore drill, perubahan terkoordinasi, rebuild dan smoke yang sama **tersendiri** pada `20.20.20.3`. Pastikan kedua host menolak token/key dari host lain dengan uji aman terkontrol, tanpa merekam token atau material kunci. Jalankan verifier `npm run verify:phase13-credential-isolation` dengan enam input privat `PHASE13_{DEV,PROD}_{JWT_SECRET,SUPABASE_SERVICE_ROLE_KEY,SUPABASE_ANON_KEY}`; hanya simpan hasil lulus/gagal yang tidak mengandung secret.
5. Lepas freeze tiap host hanya setelah health, integritas data, Auth, Storage, semua writer dan rollback readiness disetujui pemilik. Monitor 401/403, refresh failures, gateway, PostgREST, Storage, Realtime, login serta operasi aplikasi bersama sepanjang masa tenggang. Baru nyatakan selesai setelah semua klien pindah dan isolasi lintas host teruji.

## Sesi lama dan masa tenggang

Rotasi `JWT_SECRET` self-hosted menggugurkan verifikasi **semua JWT lama** yang ditandatangani secret itu: access token pengguna, anon/service-role JWT, signed URL dan token integrasi terkait. Refresh token tersimpan di Auth bukan jaminan sesi tetap berjalan jika Auth/Kong/verifier berubah; uji refresh pada clone dan rencanakan login ulang. Tidak ada asumsi verifier otomatis menerima dua secret lama/baru. Pemilik harus memilih dan mengumumkan kebijakan: masa tenggang **sebelum** cutover untuk memperbarui klien dan memberi notifikasi pengguna, atau skema dual-key yang dibuktikan didukung oleh **seluruh** signer/verifier dalam rehearsal dengan batas kedaluwarsa tegas. Jika dual-key tidak terbukti, jadwalkan pemutusan sesi dan re-login dalam maintenance; jangan mempertahankan secret bersama di production demi kompatibilitas. Tetapkan durasi dari TTL token/signed URL dan kebutuhan pengguna, deadline pencabutan key lama, serta kriteria monitor/penutupan secara tertulis. Jangan menyebut rotasi selesai selama token lintas host lama masih diterima.

## STOP dan rollback

- Sebelum perubahan secret: bila persetujuan, freeze, backup konsisten atau restore drill gagal, batalkan window; tidak ada rollback konfigurasi diperlukan.
- Sesudah perubahan: hentikan writer dan traffic berisiko; diagnosa ketidakcocokan komponen atau image terlebih dahulu. Roll-forward konfigurasi baru yang sudah disetujui lebih aman jika data sudah ditulis dengan secret baru. Rollback ke secret lama yang **identik lintas host** menghidupkan kembali risiko lintas lingkungan dan memutus sesi/key baru; hanya lewat persetujuan insiden bersama kedua host, dengan batas waktu, mitigasi akses, dan jadwal rotasi ulang. Jangan rollback satu komponen/host diam-diam.
- Jika ada perubahan data/schema selama window dan rollback image saja tidak cukup, pulihkan replacement dari backup final konsisten DB/Auth/roles/config/Storage, uji restore, lalu alihkan endpoint sesuai runbook cutover. Tentukan nasib write setelah backup dengan pemilik data sebelum restore agar tidak hilang diam-diam. Simpan artifact gagal untuk forensik, batasi akses secret, catat waktu, keputusan, dan bukti uji tanpa nilai rahasia.
